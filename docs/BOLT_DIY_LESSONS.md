# Bolt.diy 学习笔记

这是把同级目录里的 `bolt.diy` 拆出来看后，适合 `chat2app` 借鉴的部分。重点不是照搬它的体量，而是借它的工程组织和产品思路。

## 一句话结论

Bolt.diy 的核心价值不是“能生成代码”，而是把聊天、文件、终端、预览、历史、Git 同步和模型选择组织成一个完整的浏览器工作台。

`chat2app` 不需要完全变成 AI IDE，但可以借它的分层方法，把“生成、修改、验证、回退”做得更稳。

## 最值得学的 5 件事

### 1. Prompt 分层很清楚

Bolt.diy 不是一套 prompt 走天下，而是把系统提示分成了不同场景：

- 简化 prompt
- 完整 prompt
- diff / patch 风格修改 prompt

这和 `chat2app` 现在的三档思路很一致：

- 新建应用：少量上下文 + 生成规则
- 普通修改：当前 HTML + 历史需求 + 新需求
- 复杂修复：相关代码片段 + 浏览器错误

### 2. 它把“修改代码”当成有状态流程

Bolt.diy 里，文件保存、未保存状态、diff、回退、工作台切换不是附属能力，而是核心工作流的一部分。

这比“只生成一份结果”更像真正的开发体验。

对 `chat2app` 的启发是：

- Patch 不只是补丁文本，而是可追溯修改
- 版本不只是文件覆盖，而是可回退的状态点
- 浏览器验证不只是检查，而是修改链路的一部分

### 3. 聊天历史是工作记忆，不是日志

Bolt.diy 的历史不是简单存消息，而是把：

- 对话
- 项目状态
- 回退点
- 导入来源
- 版本信息

绑在一起。

这很值得学，因为它让用户重新打开项目时，不只是“看到旧聊天”，而是“回到上次工作现场”。

### 4. 它把导入已有项目做成入口能力

它会自动识别：

- `package.json`
- `index.html`
- 可运行命令

然后给出合适的启动方式。

这个思路很实用。哪怕 `chat2app` 仍然以单文件 PWA 为主，也可以继续借鉴“自动识别项目类型”和“自动选择执行路径”。

### 5. 它把 Git / GitHub 当成产品动作

Bolt.diy 不是把 Git 当成底层命令，而是把它做成用户可理解的动作：

- 导出
- 推送
- 回退
- 历史对照

这点对 `chat2app` 也有启发，但不一定要照搬真实 Git。你现在的“Git 风格版本管理，但不实际使用 Git”就已经是更轻的一版。

## `chat2app` 已经有、或者已经接近的部分

- 轻量上下文管理
- 严格 Patch 协议
- 版本化发布和回退
- 浏览器验证与自动修复
- 失败现场保留
- 交互验收
- 模型适配层

当前还补齐了与 Bolt.diy 上下文工作流对应的结构化记录：

- 每次迭代记录上下文策略、复杂度、历史条目数和实际送入模型的代码长度；
- 每次生成记录使用 Patch 还是完整 HTML；
- 版本记录保留 Diff 摘要、校验状态、摘要哈希和父版本；
- 浏览器错误、自动修复开始/结束和失败原因进入 SSE 与会话现场；
- 应用详情可以读取最近一次工作流元数据，便于诊断和恢复。

这仍然不是 Bolt.diy 的多文件工具调用模型，而是面向单 HTML 应用的轻量等价物。

这些其实已经在往 Bolt.diy 的“工作流化”方向靠了，只是保持了更轻的产品形态。

## 不建议直接照搬的部分

- 不要直接做成完整 WebContainer IDE
- 不要把终端、文件树、预览、GitHub、模型切换全部堆满
- 不要为了像 Bolt 而把复杂度推成通用 AI 开发平台

`chat2app` 的核心还是：

- 轻
- 快
- 单文件输出
- 可验证
- 可回退

## 如果要继续借鉴，优先级我会这样排

1. Prompt 分档和上下文收缩
2. Patch / diff / 回退链路
3. 聊天历史和状态恢复
4. 导入项目时的命令探测
5. 再考虑多 provider / 多模型 UI

## 结尾

一句话说完：Bolt.diy 值得学的是“把 AI 编码做成工作台”，而不是“把 AI 编码做得更大”。

对 `chat2app` 来说，最合适的方向是继续保持轻量，但把生成、验证、修复、回退这条链路做得更像一个完整产品。
