# Chat2App 项目进展与演进路线

更新时间：2026-08-13

## 一、总体方向

Chat2App 不照搬 Aider 的复杂度，而是借鉴其核心思想，保持纯 JavaScript/TypeScript、单文件 PWA 和轻量部署模式。

当前目标链路：

```text
需求
  ↓
轻量规划
  ↓
增量编辑
  ↓
浏览器验证
  ↓
错误反馈自动修复
  ↓
版本化发布
```

## 二、已完成能力

### 1. TypeScript 与任务系统

- `server.ts` 作为主源码，`server.js` 保留兼容入口。
- TypeScript 构建、类型检查和 HTTP 测试已建立。
- 异步生成任务、任务持久化、队列、并发限制、自动重试和取消已完成。
- 任务支持 SSE 事件重放，页面刷新后可以恢复未完成任务。

### 2. 完整聊天历史

应用的 `session.json` 现在同时保存：

- 用户每次需求；
- DeepSeek 的完整文字反馈；
- 生成过程中的状态和结果；
- 最终应用版本信息。

模板化流程已压缩为一条摘要：

```text
✅ 已完成：代码生成、PWA 打包、验证并发布
```

历史恢复时仍会显示完整的用户需求和模型反馈，不再只保留用户输入。

### 3. 规划与增量编辑

- 新应用请求会要求模型先输出轻量实现计划。
- 迭代请求优先要求模型输出 `SEARCH/REPLACE` Patch。
- Patch 可以精确修改现有 HTML，减少无关内容变动。
- Patch 格式不合法、匹配不唯一或模型返回完整 HTML 时，自动回退到完整 HTML 流程，保持兼容性。

### 4. 浏览器验证与自动修复

- 已集成可选的 Playwright Chromium 无头验证。
- 验证页面 HTTP 状态、`pageerror` 和浏览器 console error。
- 验证失败后，会把错误反馈给 DeepSeek，请求生成修复后的 HTML。
- 修复后再次验证；仍失败才终止发布并向用户报告。

服务器当前已配置：

```env
BROWSER_VALIDATION=true
BROWSER_EXECUTABLE=/usr/bin/google-chrome
```

### 5. 版本化发布

- 每次迭代前备份旧版 HTML 到 `versions/`。
- 应用版本号递增。
- 支持回退到上一版。
- 仍保持单 HTML PWA 的产品形态，不改变最终用户访问方式。

### 6. 上下文与失败现场记录

- 迭代请求记录上下文策略、复杂度、历史条目数和代码裁剪比例。
- SSE 记录本次编辑采用 Patch 还是完整 HTML。
- 版本记录保存 Diff 摘要、校验状态、摘要哈希和父版本。
- 浏览器错误、自动修复尝试和最终失败原因会进入任务/会话现场。
- 应用详情 API 返回最近一次工作流元数据，便于诊断和恢复。

### 7. 对照 Aider / Bolt.diy 的核心借鉴

- 轻量上下文管理：新应用、普通迭代、复杂修复三种上下文策略。
- 严格 Patch 协议：唯一 `SEARCH` 匹配、预校验、失败回退、原子写入。
- Git 风格版本管理：`create / patch / rollback` 都会生成版本提交，但不实际依赖 Git。
- 浏览器验证链路：可选无头验证、失败自动修复、再次验证后再发布。
- 交互验收：支持 `click / fill / press / assert`，可把保存、刷新恢复、计数器等真实用户路径写成验收步骤。
- 失败现场保留：保存最近事件、错误信息和尝试次数，便于复盘。
- 模型适配层：把流式和非流式请求收口到统一适配器。
- 单文件 PWA 产物：最终仍输出一个可直接访问、可安装的 HTML 应用。

当前更像 Aider 的地方在于：

- 会优先保留上下文中的“可复用部分”，而不是一股脑把所有历史都塞给模型。
- 会优先尝试局部 Patch，而不是每次都重写整个文件。
- 会用浏览器结果反向修复，而不是只看文本输出就结束。
- 会保留版本链和回退点，方便把每次修改当成一次可追溯提交。

Bolt.diy 的启发不在于复制 WebContainer、终端、Electron 或多文件 IDE，而在于把 AI 编码看作一条可观测工作流：聊天历史、上下文收缩、局部修改、运行验证、修复和回退彼此关联。Chat2App 已实现面向单 HTML PWA 的轻量等价物。

不纳入当前范围的能力：完整浏览器 IDE、终端/文件树、多模型平台、MCP 生态、Supabase 和 Electron。它们会改变产品定位，却不能直接提升单文件小应用的交付质量。

### 8. 应用级一致性与并发保护（OpenHands 思路，前两档已落地）

`tasks-data/` 与 `apps-data/` 的职责不同：前者保存生成任务的排队、重试和恢复状态；后者保存某个应用的 HTML、会话和版本记录。过去的风险不在于两个目录天然“交叉”，而在于同一应用的生成、Patch 或回退如果同时写入，可能基于不同版本读写，造成版本号、快照和 `session.json` 不一致。

当前针对单个应用建立了轻量的单写者提交模型：

```text
生成 / Patch / 回退请求
          ↓
按 appId 获取短时写锁（冲突请求返回 409）
          ↓
预校验 → 原子写入应用文件 → 记录版本提交
          ↓
更新 session.json 工作流状态（validating → idle）
          ↓
释放写锁
```

- 生成、Patch、回退共用同一把应用级锁；同一应用不会发生并发覆盖，不同应用仍可并行。
- Patch 会先完成全部匹配和 HTML/JS 校验，再一次性写入，避免“写到一半失败”。
- 每次变更保留版本快照和提交记录；回退也在锁内执行，并刷新会话头指针。
- `session.json.workflow.state` 明确标记当前处于验证还是空闲，便于前端展示和故障排查。

这相当于借用 OpenHands 的“工作区单写者 + 可恢复提交点”思想，但没有引入容器沙箱、真实 Git 分支或跨进程分布式锁。当前锁是进程内的：服务重启会自然释放锁，持久化工作流状态和版本快照用于恢复判断。跨实例部署、长时运行隔离和分布式锁属于第三档，暂不做。

## 三、部署链路

```text

  ↓ git commit / git push
GitHub
  ↓ Actions：npm ci、构建、测试
腾讯云服务器
  ↓ git pull、npm ci、npm run build
systemd 重启 chat2app.service
```

- 进程管理：`chat2app.service`
- 数据目录：`apps-data/`、`tasks-data/`
- 当前代码版本：`b4341e2`

服务器 `.env` 只保留在服务器，不进入 Git，也不会被自动部署覆盖。

## 五、当前边界

- 规划是轻量提示阶段，不是独立的多 Agent 规划器。
- Patch 是优先策略，不强制要求模型每次都返回 Patch。
- 自动修复目前最多进行一轮修复和再次验证。
- 浏览器验证会增加生成耗时；只有验证失败时才会额外调用一次 LLM。
- 当前仍以单 HTML PWA 为最终产物，暂不引入复杂多文件工程。

## 七、下一阶段计划：稳定性加固

下一阶段暂不扩展复杂 Agent 架构，重点验证和加固当前链路。

### 1. 自动化回归测试

- 测试 Patch 成功应用。
- 测试 Patch 不合法时回退完整 HTML。
- 测试浏览器验证失败后自动修复。
- 测试自动修复失败时正确终止。
- 测试版本发布与回退。
- 测试失败任务的历史恢复。

### 2. 线上端到端验收

按以下流程实际验证：

```text
新建应用 → Patch 迭代 → Chrome 验证 → 自动修复 → 版本回退
```

建议使用简单计数器作为验收样例，连续进行两到三次修改，并观察服务日志和页面历史。

### 3. 完整记录失败过程

当前成功任务已经会保存完整聊天历史。下一步补齐失败任务的过程恢复，让用户也能看到：

- DeepSeek 已输出的反馈；
- 浏览器验证错误；
- 自动修复尝试；
- 最终失败原因。

推荐顺序：先进行线上验收，再根据真实失败样本补测试和失败历史，避免脱离实际使用场景扩展功能。

## 九、当前结论与下一步

本阶段的能力建设已完成，项目可从“继续借鉴 Aider / Bolt.diy”转入“真实使用驱动的稳定性优化”。

后续持续记录四项指标：

- Patch 命中率与完整 HTML 回退率；
- 浏览器验证失败率；
- 自动修复触发率与成功率；
- 生成耗时与模型调用成本。

只有出现真实失败样本时，再针对性补 Patch 提示、上下文选择、浏览器交互验收和回归测试。下一次有明确扩展需求时，优先把 `server.ts` 中的生成编排、版本存储和会话存储拆为独立模块，而不是继续堆叠到单个文件。
